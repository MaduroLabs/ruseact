# M4.4.4 — Keyed Lists and Stable DOM Identity

Status: implementation on `feature/m4.4.4-keyed-lists`; review and hosted CI
verification are required before this milestone is considered complete.

## Scope

M4.4.4 adds keyed-only list regions to the existing renderer. A list is an
explicit structural computation driven by one application-owned scalar
revision signal. The collection remains in JavaScript; RustReactiveCore does
not store arrays or objects. A list retains an item owner when its key remains
present and moves the item's existing DOM range when order changes.

The existing root API, one-shot mounting, manual one-pass flush, component
setup rules, conditional regions, and structured results remain unchanged.
There is no virtual DOM, generic tree diff, scheduler, implicit tracking, or
unkeyed list behavior.

## Version 4 plan contract

`ruseact.template` version 4 extends the version 3 plan with:

```ts
interface KeyedListPlan {
  readonly kind: "keyed";
  readonly id: string;
  readonly parentId?: string;
  readonly order: number;
  readonly dependencies: readonly SignalHandle<SupportedScalar>[];
  readonly evaluate: (context: BindingEvaluationContext) =>
    RendererResult<readonly KeyedItemDescriptor[]>;
  readonly createItem: (environment: KeyedItemEnvironment) =>
    RendererResult<ComponentView>;
}
```

The public `packages/ruseact-dom` entry point exports the version 4 plan and
item descriptor types, but not anchors, owner records, structural handles, or
host internals. Versions 1, 2, and 3 remain independently validated and use
the same renderer pipeline. Older versions reject keyed metadata.

## Key identity and preflight

The only valid structural keys are non-null strings, booleans, and finite
numbers. `NaN`, infinities, objects, arrays, symbols, functions, `bigint`,
`null`, and `undefined` are rejected. A native `Map` supplies SameValueZero
semantics: `+0` and `-0` are one key, while `1`, `"1"`, and `true` remain
distinct. Diagnostic strings never determine identity.

The complete evaluator result is copied into a stable snapshot before any
DOM mutation, item signal write, item factory call, or item disposal. Missing
keys, duplicate keys, invalid scalar fields, and retained-schema changes fail
before mutation and preserve the published map, order, owners, and DOM.

## Collection publication and item data

Applications own the JavaScript collection and publish changes explicitly:

1. Replace or mutate the application collection according to its own policy.
2. Write a changed scalar revision signal.
3. Call `root.flush()`.

Mutating the collection without the revision write does not schedule a list
update. The evaluator reads the current collection during execution; each
execution snapshots its descriptors so later collection mutation cannot alter
published item records.

Item fields are a narrow record of supported scalar values. New items receive
renderer-owned scalar signals for those fields. Retained items preserve the
same owner, component instances, DOM nodes, listeners, computations, and
field signal handles. Changed field values use `ReactiveCore.set()`; unchanged
writes retain the existing equality behavior. Retained setup is never rerun
and immutable component props are never replaced. Renderer-owned item signals
are disposed after their dependent resources; application-owned signals are
always borrowed and survive root cleanup.

## Anchors and reconciliation

Each list and item owns a stable private start/end comment-anchor pair. An item
range can be empty, single-root, or multi-root and can contain supported
components, conditional regions, and nested lists. Range validation proves
same-document ownership, expected parentage, anchor order, exact owner
membership, and direct range membership before mutation. Foreign or
externally relocated nodes fail closed and are never adopted or deleted.

Reconciliation is deterministic and keyed-only:

1. Snapshot and validate the complete next collection.
2. Compute retained, removed, and inserted keys with `Map` lookup.
3. Stage new item owners, field signals, factories, and child plans.
4. Dispose removed items child-first.
5. Update retained field signals.
6. Walk desired order from right to left and move verified ranges before the
   next verified anchor using the existing host insertion operation.
7. Validate the resulting ranges and publish the new map/order.

No Longest Increasing Subsequence optimization is used. No-op order performs
no native movement. Retained nodes and listeners are moved, not recreated.
The browser fixture also verifies retained uncontrolled input values and
records the actual focus behavior of native movement; the renderer does not
manually restore focus or promise cross-browser selection preservation.

## Flush and ownership

Keyed structural computations register in the existing `BindingContext` and
share RustReactiveCore's pending queue with scalar and conditional records.
FIFO snapshot order, deduplication, reentrant-flush rejection, one-pass
draining, and deferred newly generated work are unchanged. A retained field
write may enqueue a scalar binding for a later explicit flush. A binding
already in the current snapshot executes normally and reads the new value.

If a list removes an item whose computation is later in the validated
snapshot, the existing exact-disposal provenance permits that exact record to
be skipped and counted in `FlushReport.skippedCount`. Unknown, foreign,
malformed, unexpectedly missing, or unsuccessfully disposed computations are
still errors. Slot reuse cannot make an old identity equal to a new one.

The list owner is beneath the existing root owner. Item cleanup disposes
descendants, computations/subscriptions/listeners, dependent bindings, owned
field signals, and verified DOM resources in the required order. Successful
item records are released from the active parent map. Failed cleanup retains
ownership metadata and fails closed; arbitrary application side effects and
full transactional DOM rollback are not claimed.

## Provisional compiler marker

The private TypeScript Compiler API transform accepts the narrow provisional
form:

```tsx
ruseact.keyed(
  [revision],
  ({ runtime }) => ({
    ok: true,
    value: items.value.map((item) => ({
      key: item.id,
      fields: { label: item.label },
    })),
  }),
  ({ fields }) => (
    <span>{ruseact.bindText([fields.label], ({ runtime }) =>
      runtime.get(fields.label))}</span>
  ),
)
```

This is compiler-only and provisional, not a general JSX `key` contract.
Dependencies remain explicit, item factories are lazy, closures are preserved,
and runtime key validation remains authoritative. Unkeyed arrays, implicit
tracking, spreads, arbitrary object fields, and dynamic structural expressions
are rejected.

## Failure and compatibility policy

Validation failures before mutation preserve the previous published state.
New item initialization rolls back renderer-managed resources where safe. Once
native mutation begins, the renderer records actual ownership and does not
pretend arbitrary operations are transactional. Failed item cleanup or range
mutation preserves original and cleanup diagnostics and prevents unsafe later
updates. A removed key that returns receives a fresh activation identity; old
items are never resurrected.

## Verification and benchmark plan

The authoritative browser command is:

```sh
RUSEACT_BROWSER_BINDGEN_OUT=target/m4.4.4-browser-bindgen \
  corepack pnpm test:browser:keyed
```

It uses real Rust/WASM, the public `createRoot`, static version 4 plans, the
compiler-generated version 4 fixture, insert/prepend/reorder/removal, retained
data, duplicate and mixed key types, deferred scalar updates, cleanup, and
borrowed-resource checks. Hosted Chromium is authoritative when InstaBox
cannot bind its temporary localhost server.

`benchmark:browser:keyed` measures bounded append, prepend, reverse, and
no-op reconciliation workloads at 10, 100, and 1000 items. It reports actual
operation counts, raw positive samples, metadata, and integrity status. It is
not a comparative React benchmark and introduces no new acceptance threshold.

## Deferred work and M4.5 handoff

Unkeyed lists, implicit key generation, object keys, array/object Rust
signals, proxy tracking, component rerendering, hooks, scheduling, VDOM,
generic diffing, LIS optimization, automatic focus restoration, async lists,
SSR, hydration, portals, and new Rust/WASM ABI are deferred.

M4.5 consumers may use version 4 plans only through the public renderer and
must publish JavaScript collections with explicit revision signals. Before a
consumer repository adopts this capability, it should consume the versioned
types, run the hosted Chromium fixtures, and document the observed native
focus/selection behavior for its supported browser targets.
