# M4.5.1 experimental package distribution

## Status and scope

M4.5.1 adds a reproducible local distribution pipeline for the three existing
workspace packages. It produces installable tarballs for `ruseact`,
`ruseact-dom`, and `ruseact-compiler`; it does not publish them to npm, create
tags or releases, or modify the separate `ruseact-example` repository.

The original M4.5.1 distribution package version was `0.1.0-alpha.0`. The
M4.5.1.1 refresh produces `0.1.0-alpha.1`; neither package version is a
renderer-template protocol version. The distributed runtime supports template
protocols 1, 2, 3, and 4 through the existing renderer.

The implementation is intentionally an artifact pipeline, not a new renderer,
reactive engine, scheduler, compiler language, or framework API.

## Approved distribution decisions

The implementation follows the eight M4.5.1 decisions:

1. Local tarballs are the distribution format. No registry publication is
   performed.
2. The existing three package boundaries are preserved.
3. Packages emit ESM JavaScript, declarations, and JavaScript source maps.
4. The real release WASM binary and matching `wasm-bindgen` glue are shipped
   inside `ruseact`.
5. `ruseact-compiler` is a build-time package and is not a browser runtime
   dependency.
6. All three package artifacts use the synchronized experimental version and
   record provenance in a machine-readable manifest.
7. Verification installs the tarballs in a temporary consumer outside the
   workspace and exercises installed files only.
8. Template protocols 1–4 and their explicit manual-flush semantics remain
   unchanged.

## Package boundaries and dependency graph

```text
ruseact-dom  ──exact dependency──>  ruseact  ──packaged WASM assets

ruseact-compiler  ──build-time dependency──>  typescript@5.9.3
```

The source workspace uses `workspace:0.1.0-alpha.1` for the DOM package so
that the lockfile can validate the monorepo relationship. The distribution
staging step writes the exact package version into the staged DOM manifest;
the packed tarball contains no `workspace:` dependency. A consumer installs
the three artifacts as a matching set.

The packages remain `private: true`: this prevents accidental registry
publication while still allowing standard `pnpm pack` tarball installation.
The package entry points expose only the public package roots and the two
documented WASM loader subpaths. Private host, binding, root, ownership, and
raw bridge modules are not exported.

The DOM package imports runtime types and values from the canonical `ruseact`
package name. It does not embed or compile a second runtime implementation.
This preserves the identity of installed `SignalHandle` and
`ComputationHandle` values across the runtime and renderer package boundary.

## Package output

The build uses ordinary TypeScript emission rather than a bundler:

```text
target/distribution/package-build/<package>/
  package.json
  dist/index.js
  dist/index.d.ts
  dist/index.js.map
```

The generated JavaScript is ESM. Declarations and source maps are emitted for
each package, and built imports use package boundaries or package-local `.js`
paths rather than workspace source paths. The TypeScript configuration used by
the distribution build maps the DOM package's `ruseact` type import to the
staged runtime declarations, which keeps declaration generation independent of
the source workspace layout.

The compiler package exposes the existing `compileTsxModule` entry point and
its diagnostics and metadata types. It retains the supported TSX subset and
the deterministic version 1–4 output selection. It is not bundled into either
browser package and is not required after TSX has been compiled.

## WASM packaging and initialization

The distribution build performs a locked release build for
`wasm32-unknown-unknown`, then runs the pinned `wasm-bindgen` CLI (`0.2.130`)
for both supported generated targets:

```text
ruseact/wasm/node/ruseact_wasm.js
ruseact/wasm/node/ruseact_wasm.d.ts
ruseact/wasm/node/ruseact_wasm_bg.wasm
ruseact/wasm/web/ruseact_wasm.js
ruseact/wasm/web/ruseact_wasm.d.ts
ruseact/wasm/web/ruseact_wasm_bg.wasm
```

The Node glue emitted by this pinned toolchain is CommonJS. The package
therefore includes a private nested `wasm/node/package.json` with
`{"type":"commonjs"}` while the package root remains ESM. The web glue is
an ESM module and must be initialized explicitly by the consumer.

The runtime package itself never initializes WASM on import and does not
create a global runtime. The existing loader boundary remains
`createReactiveCore(loadWasm)`.

Browser initialization using the installed package is:

```ts
import initializeWasm, * as wasm from "ruseact/wasm/web";
import { createReactiveCore } from "ruseact";

await initializeWasm();
const runtimeResult = await createReactiveCore(() => wasm);
if (!runtimeResult.ok) throw new Error(runtimeResult.error.code);
const runtime = runtimeResult.value;
```

For Node, the installed Node-target glue is imported from the package
subpath, and the existing explicit runtime loader is still used:

```ts
import * as wasm from "ruseact/wasm/node";
import { createReactiveCore } from "ruseact";

const runtimeResult = await createReactiveCore(() => wasm);
if (!runtimeResult.ok) throw new Error(runtimeResult.error.code);
```

Consumers do not need Rust or `wasm-bindgen` to use the packaged artifacts.
The browser must serve `.wasm` with an appropriate WASM MIME type and must
resolve the package's relative asset URL. No external CDN or machine-local
path is used.

## Build, pack, and validate

The root commands are:

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm build:distribution
corepack pnpm pack:packages
corepack pnpm test:distribution:version
corepack pnpm validate:distribution
corepack pnpm test:packages
```

`build:distribution` cleans only the ignored `target/distribution` directory,
builds the release WASM, generates both glue targets, and emits the three
package builds. `pack:packages` creates tarballs and
`distribution-manifest.json`. `validate:distribution` checks package metadata,
entry points, declarations, source maps, WASM assets, checksums, and the
absence of workspace or source-directory imports. `test:packages` installs the
tarballs into an isolated temporary consumer and runs Node, TypeScript, and
real Chromium checks.

The generated artifacts are intentionally ignored build outputs. They are not
committed to the repository.

## Artifact manifest and provenance

The manifest is written to:

```text
target/distribution/distribution-manifest.json
```

It records the repository, source commit, clean/dirty source status and paths,
package versions, artifact filenames, compressed and unpacked sizes, SHA-256
checksums, WASM targets, supported template protocols, and toolchain versions.
The source SHA identifies the base revision only when the source tree is dirty;
the manifest explicitly records that limitation. It is not a signature or
cryptographic supply-chain attestation.

The original M4.5.1 alpha.0 verification generated:

These values are generated-artifact measurements, not permanent release

clean-build comparison.

## M4.5.1.1 alpha.1 distribution refresh

M4.5.1.1 refreshes all three synchronized private package manifests to
`0.1.0-alpha.1` so the promoted M4.4.5 owner-scoped structural identity fix
can reach the independent consumer. M3.5.1 benchmark calibration hardening is
already present in the base revision and is retained. The DOM source manifest
uses `workspace:0.1.0-alpha.1`; the staged and packed DOM manifest contains
the exact dependency `ruseact@0.1.0-alpha.1`.

Active version resolution is centralized in
`scripts/distribution_metadata.mjs`. The build, pack, validation, and
installed-package test scripts derive the expected version and package names
from the three source manifests, reject mismatched versions or dependencies,
and require artifact filenames to match the resolved version. The dedicated
`test:distribution:version` command covers source-version, packed-dependency,
filename, and private-package regressions.

The local feature-branch build below is a development artifact from a dirty
working tree. Its source commit identifies the branch base only; it is not the
authoritative post-promotion consumer handoff set:

only then update the consumer repository's vendored artifacts.

## Isolated consumer verification

The verification harness creates a temporary directory outside the repository,
copies the three tarballs there, installs them with pnpm, and runs strict
TypeScript checking against the installed declarations. It does not import
`packages/*/src`, use workspace symlinks, or reference the repository's WASM
output. A local `pnpm` override is used only because these private tarballs
have no registry entry; it points the exact DOM dependency at the copied
runtime tarball and does not alter the packed manifest.

The installed consumer verifies:

- Node runtime initialization and scalar signal operations with packaged WASM.
- Compiler import, diagnostics, deterministic generated ESM, and protocol
  versions 1–4.
- Version 1 static rendering and cleanup.
- Version 2 one-shot component setup and cleanup.
- Version 3 explicit conditional replacement and sibling identity.
- Version 4 keyed retention, reorder, retained scalar data, deferred binding
  work, and cleanup.
- A runtime-only consumer containing no compiler package.
- Actual installed package identity across `ruseact` and `ruseact-dom`.

The Chromium fixture serves the installed files through a temporary HTTP
server, including the packaged web WASM assets, and uses the public package
entry points. It is a package acceptance fixture, not an example application.
Hosted Chromium remains the authoritative CI environment.

## Compatibility and limitations

Package versioning and template protocol versioning are separate. Matching
`0.1.0-alpha.1` package artifacts preserve versions 1–4, explicit signal
dependencies, one-pass manual flush, component setup, structural ownership,
and cleanup semantics. Mixed-version package sets are not a supported
compatibility promise.

The pipeline does not add CommonJS package output, a bundler plugin, runtime
TSX compilation, automatic scheduling, implicit dependency tracking, React
compatibility, publishing, signing, or production-readiness guarantees. The
current local InstaBox has Node `22.23.3` while the repository pins Node
`24.22.3`; local measurements record the actual host, and CI uses the pinned
`.nvmrc` version. The compiler and browser checks should therefore be
considered together with the CI results before distribution artifacts are
treated as a reviewed handoff.

## M4.5.2 consumer bootstrap handoff

M4.5.2 may consume the matching tarballs listed in the manifest, install
`ruseact` and `ruseact-dom` for browser runtime use, and install
`ruseact-compiler` as a build-time dependency. It must preserve the explicit
WASM initialization sequence, use public package roots and documented WASM
subpaths, serve web WASM correctly, and compile TSX before browser execution.
It must verify the actual status and access of `MaduroLabs/ruseact-example`
before making any repository assumptions. M4.5.1 does not create or modify
that repository and does not implement consumer applications.
