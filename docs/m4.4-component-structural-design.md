# M4.4.1 component identity and structural rendering contract

Status: design-only proposal. No component, region, keyed-list, compiler, host,
Rust, WASM, or public-package implementation is part of M4.4.1.

## 1. Executive summary

M4.2 and M4.3 provide a deliberately narrow renderer: a public root mounts one
immutable version-1 static plan, scalar binding slots update existing DOM
nodes, and JavaScript explicitly flushes the Rust-owned pending computation
snapshot. M4.4 needs a contract for the next layer without turning that
pipeline into a virtual DOM or a second reactive engine.

This proposal recommends a conservative hybrid:

- M4.4.2 runs a function component once per instance, gives it a hierarchical
  JavaScript-owned resource scope, and uses existing fine-grained bindings for
  scalar updates. Component functions do not rerun merely because a signal is
  dirty.
- M4.4.3 adds explicit anchored conditional regions. A region owns its active
  branch and selector computation, and replaces only that region's resources
  and DOM range.
- M4.4.4 adds keyed-only lists. A region keeps a key-to-item record map and
  moves retained DOM nodes with native host operations; it does not compare
  two application-wide trees.

The recommendations are not approved public contracts. Human approval is
required for identity, anchor representation, key equality, compiler protocol
versioning, and structural error recovery before implementation begins.

## 2. Verified implementation baseline

The following facts are implemented on the M4.3 baseline and are constraints
on this proposal.

### Runtime and ownership

`ReactiveCore` stores scalar boolean, finite number, and string values. Signal
reads do not implicitly subscribe a computation. Computations are metadata
identities; Rust propagates dirtiness and owns the FIFO pending queue but does
not execute JavaScript callbacks. The WASM bridge transfers validated opaque
identities and structured errors.

`packages/ruseact-dom/src/host.ts` owns created Element and Text nodes and a
claimed Element or DocumentFragment container. It validates document, host
context, ancestry, insertion anchors, detached nodes, attributes, the narrow
`value`/`checked`/`disabled` property set, and native listener identity.
Staged subtrees may be assembled before reaching their claimed container;
mounted nodes must continue to reach that boundary. Comments and dedicated
anchor nodes are not currently supported host node kinds.

`BindingContext` creates legitimate computation handles, records explicit
signal dependencies, evaluates JavaScript callbacks initially and during one
explicit flush, and disposes subscriptions and computations. The pending
drain is global and destructive for one runtime. Therefore one active mounted
binding context requires one dedicated `ReactiveCore`; M4.4 must not silently
relax that restriction.

`RootContext` owns the existing lifecycle states `created`, `mounting`,
`mounted`, `unmounting`, `unmounted`, `cleanup_failed`, and `disposed`. It
borrows the runtime and container, owns renderer-created resources, rolls back
mount failures, and refuses to claim a container already owned by another
root. Successful unmount releases the container for a new root, but the old
root is one-shot and cannot remount.

### Public renderer and compiler

M4.2 exports `createRoot`, `RendererRoot`, `RendererResult`, and
`ViewDescription` version 1 from `ruseact-dom`. A view instantiates one
`ViewInstancePlan` containing static Element/Text nodes, explicit parent IDs,
scalar binding slots, and native listener plans. Validation happens before
most DOM mutation and execution lowers into the existing root mount scope.

M4.3 uses the TypeScript Compiler API to emit that same version-1 plan for a
limited lowercase intrinsic JSX subset. It supports explicit provisional
`ruseact.bindText`, `bindAttribute`, and `bindProperty` markers, preserves
closures, and rejects components, fragments, lists, conditional structure,
implicit dependencies, and unsupported namespaces. The compiler does not yet
emit structural instructions.

## 3. Component execution alternatives

### A. One-shot setup with fine-grained slots

A component function executes once, returns or constructs static content, and
registers bindings and listeners. Signals update slots but never rerun the
component.

This has the smallest semantic surface and preserves closure and DOM identity.
It cannot express structural changes without an explicit region API.

### B. Component re-execution

A changed prop or structural dependency reruns a component and applies the
result to its existing instance.

This is expressive, but requires an identity-preserving plan update protocol,
child matching, listener replacement, keyed moves, ownership transfer, and
rollback semantics. A rerun-and-patch mechanism would be a renderer engine,
not a small extension to M4.2.

### C. Recommended conservative hybrid

Use one-shot setup for component instances. Add re-execution only at explicit
structural-region boundaries approved later. Scalar changes remain targeted
bindings. A structural region can own a branch factory or keyed item factory,
but the component function itself is not an implicit scheduler task.

This keeps the current execution path intact while providing a place to define
conditional and list replacement precisely. It also makes component cleanup
independent from computation identity: one component can own many bindings,
and one binding is never evidence that its component should rerun.

### Function and props model

A future component should be a JavaScript function with an immutable props
snapshot for one setup call. A component instance receives an owner scope and
returns a child mount plan or a narrowly typed child construction result. Its
event handlers close over the instance's props and state cells. If props are
later updated, that must be an explicit region operation; it must not mutate a
captured snapshot behind the component's back.

No `useState`, Hooks ordering, effects, or React compatibility is implied. A
future local-state design would need a stable state cell owned by the instance
and accessors that read the current cell value; simply rerunning a function
does not make old closures observe fresh state.

## 4. Component identity

### Recommended identity tuple

Proposed identity is scoped by:

```ts
interface ProposedComponentIdentity {
  readonly parentOwnerId: string;
  readonly regionId: string;
  readonly componentTypeId: string;
  readonly instanceKey: string | number | boolean | undefined;
}
```

This is a conceptual record, not an approved public type. `parentOwnerId` and
`regionId` scope identity; `componentTypeId` identifies the compiled or
registered component definition; `instanceKey` distinguishes siblings. A
compiler-generated local instance slot may fill the key for a statically
unique child. A keyed list supplies its item key.

Identity is created when a parent region accepts a child instance. It is
preserved only while the parent region, component type, and instance key remain
compatible. Replacing a region, changing an incompatible type, or removing a
key invalidates the identity and disposes descendants. Nested identities are
scoped under their parent, so two identical component functions in different
parents remain independent.

Do not use DOM order, a Rust `ComputationHandle`, a signal handle, or a global
counter as the complete identity. DOM order changes during a keyed move, and a
component can own multiple computations. A process-global counter can be a
debug aid but must not make identity retention depend on allocation history.

## 5. Hierarchical resource ownership

The proposed hierarchy is:

```text
RendererRoot
└── ComponentOwner / StructuralRegionOwner
    ├── DOM node records
    ├── Binding and computation records
    ├── Native listener records
    ├── Child component owners
    └── Child structural regions
```

Each owner is created before its first child resource and registers children
explicitly. A child cannot be adopted from another root, runtime, document, or
owner. Resources are released in reverse registration order, with descendants
cleaned before the parent removes its DOM range. The owner borrows the
application runtime, signals, and root container; it never disposes them.

Initialization is a two-phase operation: construct and register resources,
then publish the owner as active. A failure before publication disposes all
successfully registered resources. A failure during cleanup retains an
explicit `cleanup_failed` state and the ownership information needed to avoid
unsafe retries or unrelated DOM removal. The original failure and cleanup
failure must both be represented by structured diagnostics.

The root remains the outer ownership boundary. Unmount first prevents new
work, then disposes child regions/components, bindings and listeners, removes
owned nodes, and only releases the container claim after cleanup succeeds.

## 6. Structural region representation

### Anchors

A region should own a stable start and end anchor and a range record:

```ts
interface ProposedRegionRecord {
  readonly id: string;
  readonly ownerId: string;
  readonly startAnchor: Node;
  readonly endAnchor: Node;
  readonly dependencies: readonly SignalHandle<SupportedScalar>[];
  readonly children: readonly string[];
  state: "active" | "updating" | "disposed" | "cleanup_failed";
}
```

The current host accepts only Element and Text as created/insertable nodes.
Using a visible Text node as an anchor is unsafe because a text binding can
change or remove its content. The smallest future host extension is a
renderer-owned invisible comment anchor, exposed internally as something like
`createAnchor()` and covered by the same document, context, ancestry, staged
subtree, and cleanup validation. The public renderer must not expose arbitrary
comment mutation. An alternative is a private anchor node abstraction backed
by comments; it has the same host implementation requirement.

This extension is not implemented here. Human approval is required because it
expands the host node-kind contract and every disposal path must prove that an
anchor cannot be confused with user content. Anchor insertion should continue
to use native `insertBefore` and preserve browser node identity.

### Region operations

A future region operation should validate its owner, anchors, parent
container, dependencies, and child identity before mutation. It may create a
staged child subtree, attach it between anchors, and register its resources.
It must not compare a mutable old and new virtual tree. The region record is
an ownership/index structure, not a virtual DOM.

## 7. Conditional region lifecycle

Conceptual syntax such as `when(condition, thenView, elseView)` is not an
approved API. Its proposed semantics are:

1. Create anchors and register one explicit selector dependency.
2. Evaluate the selector once during region setup.
3. Create the selected branch in a child owner, run initial bindings, then
   attach its completed range between the anchors.
4. On a changed selector, run one structural update in the current flush
   snapshot. Dispose the old branch's listeners, bindings, computations, and
   nodes; create and attach the new branch; publish the new active branch only
   after successful setup.
5. If selector output is unchanged, do nothing.

The observable transitions are:

| Previous | New | Proposed result |
| --- | --- | --- |
| none | false/true | Create one selected branch. |
| false | true | Remove and dispose false branch, then mount true branch. |
| true | false | Remove and dispose true branch, then mount false branch. |
| true | true | No structural mutation. |
| false | false | No structural mutation. |

Cleanup-before-create is the conservative default because it prevents two
branches from owning the same region simultaneously. A failed new branch
should leave the region empty or retain the old branch only if the host can
prove the old branch was untouched; this choice requires approval and browser
tests for focus, selection, and input state. Cleanup failure is fail-closed,
not silently recovered.

Signal writes during a branch update remain pending for a later explicit
flush. A region update never drains recursively, schedules a microtask, or
reruns the component that created it. External removal or movement of either
anchor or a child range is a detached/foreign ownership error.

## 8. Keyed-only list contract

The first list model should be keyed-only. A list region owns a deterministic
ordered sequence and a map from key to item owner. Each key identifies an item
instance, not a DOM node ID or component type.

Proposed key type:

```ts
type StructuralKey = string | number | boolean;
```

Objects, arrays, functions, symbols, `NaN`-like unsupported signal values,
and other values are rejected unless a later contract explicitly expands the
type. Keys are metadata and are not signal values; this type restriction is a
proposal for predictable serialization and diagnostics.

### Equality recommendation

Recommend `SameValueZero`:

- `NaN` equals `NaN` if numbers are later permitted to include it;
- `+0` and `-0` are the same key;
- strings and booleans use value equality; and
- duplicate detection and retention use the same rule.

The current runtime rejects `NaN`, but specifying its structural behavior
avoids a future mismatch. `Object.is` would distinguish signed zero and treat
two `NaN` values as equal; that distinction is rarely useful for identity and
could produce surprising duplicate-key behavior. Object identity is not a
safe default because object keys would make serialization, compiler output,
and diagnostics less deterministic.

### Update algorithm

Before any DOM mutation, evaluate all next keys, reject missing/duplicate
keys, and build a new key sequence. For each retained key, preserve its item
owner, DOM nodes, bindings, and listener closures. Update the retained item's
data through an explicit item update contract; do not silently recreate its
component. For new keys, create staged child owners. Dispose removed keys.

Then walk the desired order from the end toward the beginning, using the next
known DOM anchor and native `insertBefore` to move retained ranges or insert
new ranges. This deterministic algorithm is correct before it is optimized.
It may perform more moves than a minimal edit-distance algorithm; move-count
optimization is deferred until identity and focus tests establish a baseline.

Required behavior:

- empty to non-empty creates fresh instances;
- append/prepend/middle insertion preserves retained records;
- removal disposes only removed item owners;
- reverse and arbitrary reorder move nodes without recreation;
- unchanged order performs no structural mutation;
- changed data with the same key updates the retained item through an
  explicitly defined path;
- a changed key is a removal plus a new insertion;
- missing or duplicate keys fail before mutation; and
- nested keyed regions have independent maps and owner scopes.

Unkeyed lists, index identity, implicit key generation, portals, hydration,
and cross-root moves are deferred.

## 9. Structural computation semantics

Structural computations should be legitimate computation handles registered
through the same runtime and explicit dependency mechanism as scalar
bindings. A future binding/region dispatcher may add a `structural` record
kind to the JavaScript lookup map, but it must not create a second queue or
scheduler.

The existing Rust queue remains authoritative: first dirty order, deduplication,
one destructive snapshot, FIFO dispatch, and deferred work generated during a
flush. Scalar and structural records should share one dispatch order defined
by registration order and Rust pending order. A disposed region must be
removed from the lookup map; a pending identity that cannot be resolved still
fails closed because the current drain cannot restore it.

Structural updates must reject reentrancy, stale owner records, foreign
anchors, and detached ranges. They must dispose their subscriptions only once
and preserve application signals and the borrowed runtime. No scoped drain,
automatic dependency tracking, priority queue, microtask, or animation-frame
policy is proposed here.

## 10. Compiler integration and protocol versioning

M4.3 output is `ViewDescription` protocol version 1: static nodes, scalar
slots, and listeners. It should remain valid and unchanged for existing
consumers.

Two future compatibility strategies are viable:

| Strategy | Benefit | Cost |
| --- | --- | --- |
| Add optional region fields to version 1 | Fewer protocol names; gradual rollout. | M4.2 validators must understand and reject/ignore new semantics; lifecycle differences become implicit. |
| Emit a version-2 structural protocol | Explicit capability and validation boundary; old renderers reject it safely. | New types, compiler output, and compatibility tests are required. |

Recommend a new `ruseact.template` version 2 for structural plans. Regions
change ownership, rollback, anchors, and update semantics enough that treating
them as optional version-1 fields would make capability detection ambiguous.
M4.4.1 does not approve the schema.

Future compiler additions may support component tags, explicit region
markers, and keyed-list metadata only after the runtime contract is approved.
Generated code must preserve lexical closures, source locations, explicit
dependencies, and evaluation order. It must not infer arbitrary identifiers as
signals, serialize handles, construct DOM objects in Rust, or introduce a
component scheduler. Existing M4.3 unsupported-syntax diagnostics should
remain the safe fallback until the next protocol exists.

## 11. Error and rollback policy

Future structured renderer diagnostics should remain compatible with
`RendererResult` and include stable operation/resource fields. Candidate codes
include:

| Category | Candidate codes |
| --- | --- |
| Component | `invalid_component_type`, `invalid_component_instance`, `duplicate_component_identity` |
| Region | `duplicate_region_id`, `invalid_region_anchor`, `stale_region`, `detached_structural_node`, `reentrant_structural_update` |
| Keys | `missing_item_key`, `duplicate_key`, `invalid_key` |
| Ownership | `foreign_parent`, `foreign_region`, `child_mount_failed`, `child_cleanup_failed` |
| Mutation | `interrupted_structural_mutation`, `invalid_structural_dependency` |

Validation should occur before mutation wherever possible: component type and
identity, region IDs, anchors, key sets, parent ownership, dependency handles,
and supported operations. Recoverable validation errors should leave the
previous published owner state untouched. Failures after native DOM mutation
cannot claim full transactionality; the owner enters `cleanup_failed` when
cleanup cannot prove safe recovery.

Diagnostics should preserve the original cause and any cleanup code, just as
the current root and renderer results do. No exception-only public error
system, silent retry, unrelated-node removal, or guessed reconstruction is
proposed.

## 12. Test strategy

Hosted Chromium must be authoritative for browser behavior, using the real
Rust/WASM runtime, public root, compiler-generated templates, and native DOM.
Mock-only tests are useful for validation matrices but cannot establish
ownership or focus behavior.

### Components

Test one component, nested children, multiple instances of one type, props
snapshots, closure freshness, listener identity, partial setup rollback,
child-first cleanup with reverse registration order, borrowed runtime survival,
and repeated disposal. This supersedes the earlier parent-before-child wording
in the draft test strategy.

### Conditional regions

Test initial true/false, both branch switches, no-op selector writes, stable
anchors, nested branches/components, DOM identity of unaffected siblings,
focus/selection behavior, FIFO ordering, work generated during updates,
rollback, detached anchors, and cleanup failures.

### Keyed lists

Test empty, single, append, prepend, middle insertion, removal, reverse,
arbitrary reorder, unchanged order, duplicate/missing keys, `NaN` and signed
zero policy, same keys with changed data, retained node identity, input value
and focus preservation, item event closures, nested keyed regions, and removed
resource cleanup.

### Integration and regression

Retain the M3.2–M4.3 suites. Add real WASM tests for explicit manual flush,
runtime isolation, root unmount, compiler output, and no stale computation
execution. Each test should assert DOM values, node identity, listener
behavior, ownership errors, and application signal/runtime survival rather than
only checking that an operation did not throw.

## 13. Performance and benchmark plan

M2.5 and M3.5 establish bounded calibration, actual operation counts, raw
samples, integrity metadata, and separate phases. Their direct DOM reference
is a host-mutation baseline, not a framework comparison. No performance number
is fabricated or claimed here.

Future workloads should measure separately:

- one-time component setup and nested component mount;
- conditional branch creation, switch, and no-op selector update;
- keyed insertion, removal, retained update, and reorder;
- DOM move count and mutation count;
- binding/computation/listener cleanup;
- Rust/WASM calls and pending identity dispatch;
- focus/input preservation checks outside timed loops; and
- repeated create/mount/unmount cycles and supported retention diagnostics.

Setup, timed mutation, correctness validation, and cleanup must have explicit
boundaries. Every workload needs warmups, bounded adaptive calibration,
positive finite samples, accurate operation counts, and unresolved output when
quality is insufficient. Any optimization to reduce moves or group bindings
requires measured evidence on the same hosted browser and toolchain.

## 15. Decisions requiring human approval

Before M4.4.2 implementation, approve or reject:

1. The conservative hybrid and one-shot component setup model.
2. The parent-region/type/slot-or-key component identity tuple.
3. Immutable initial props and the explicit future prop-update boundary.
4. Hierarchical child resource ownership and reverse cleanup.
5. Private comment anchors and the required internal host extension.
6. Cleanup-first conditional branch replacement and its failure behavior.
7. Key type and `SameValueZero` equality, including the `NaN`/signed-zero
   policy.
8. Explicit retained-item update semantics for same-key data changes.
9. A new structural template protocol version rather than silently extending
   M4.2/M4.3 version 1.
10. Structural records sharing the existing Rust pending queue and manual
    one-pass flush.
11. The proposed error names and fail-closed `cleanup_failed` handling.

No decision above should be inferred from this document's recommendations.

## 16. M4.4.2–M4.4.4 roadmap

### M4.4.2 — Function Components & Nested Ownership

**Objective:** implement one-shot JavaScript function components and nested
owner scopes.

**Prerequisites:** approval of component execution, identity, props, ownership,
and cleanup decisions; no new WASM ABI is required.

**Scope:** component metadata, parent-child owner registration, initial setup,
explicit scalar bindings/listeners, partial mount rollback, child-first
cleanup, public validation, and compiler support for approved component tags.

**Out of scope:** component rerendering, hooks, local-state compatibility,
conditional regions, lists, unkeyed identity, and automatic scheduling.

**Testing/CI:** real Rust/WASM Chromium tests for nested instances, duplicate
identity, closure behavior, listener cleanup, runtime isolation, and failed
setup; all existing checks remain required.

**Acceptance:** independently owned nested components mount, preserve scalar
binding identity, reject foreign adoption, clean up in reverse order, and
leave borrowed runtime/signals alive. Publish one PR from a fresh branch and
stop for human review.

**Risks:** premature props/state semantics and ownership leaks during partial
initialization.

### M4.4.3 — Conditional Structural Regions

**Objective:** implement one explicit anchored conditional region.

**Prerequisites:** M4.4.2 ownership contract, approved anchor host extension,
branch cleanup/recovery policy, and structural computation semantics.

**Scope:** private anchors, one selector dependency, true/false branch
ownership, deterministic replacement, one-pass flush integration, detached
anchor checks, rollback diagnostics, compiler metadata for approved syntax.

**Out of scope:** lists, portals, hydration, async branches, unkeyed regions,
and recursive flushing.

**Testing/CI:** real Chromium branch switches, no-op selectors, focus and
selection behavior, nested owners, work generated during update, rollback,
and cleanup failure.

**Acceptance:** only the active branch owns the range, branch changes preserve
unrelated identity, failures are structured and fail closed, and all existing
M4.2/M4.3 behavior is unchanged. Use a fresh branch from origin/develop,
publish one PR, and stop.

**Risks:** anchor support and partial native DOM mutation can make recovery
non-transactional.

### M4.4.4 — Keyed Lists & DOM Identity

**Objective:** implement keyed-only list regions with retained item identity.

**Prerequisites:** conditional/owner infrastructure, approved key type and
equality, duplicate-key preflight, retained-item update semantics, and
deterministic move policy.

**Scope:** key validation, key map, item owner lifecycle, append/prepend/
insert/remove/reorder, native moves, nested keyed regions, item cleanup, and
compiler keyed metadata.

**Out of scope:** unkeyed diffing, implicit index keys, object keys, portals,
hydration, and minimal-move optimization before measurement.

**Testing/CI:** real Chromium identity, focus, selection, input value, event
closure, duplicate/missing key, reorder, unchanged order, nested ownership,
and cleanup tests; benchmark mutation counts and lifecycle phases with strict
integrity validation.

**Acceptance:** retained keys retain their DOM and resource identity, removed
keys clean up only their resources, invalid keys fail before mutation, and
reorders are deterministic. Publish one PR from a fresh branch and stop for
human review.

**Risks:** stale item data in closures, excessive moves, and cleanup errors
during multi-item updates.

Each roadmap item is independently reviewed. None authorizes automatic merge,
promotion, a scheduler, JSX compatibility beyond approved syntax, React Hooks,
or a virtual DOM.

## 17. Explicitly deferred capabilities

The following are outside this design and require separate approval:

- React Hooks or React API compatibility;
- automatic dependency tracking;
- microtask, frame, priority, or concurrent scheduling;
- unkeyed lists and index-based identity;
- hydration, SSR, portals, and cross-document/root movement;
- asynchronous structural updates;
- arbitrary object-valued signals;
- compiler-generated implicit signal inference; and
- a recoverable/scoped pending-drain ABI for shared-runtime roots.
