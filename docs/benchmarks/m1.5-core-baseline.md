# M1.5 RustReactiveCore baseline

This is a Rust-native microbenchmark baseline for the M1.1–M1.4 core. It is
not a browser-rendering, JavaScript, WASM-bridge, DOM-commit, memory, or
cross-framework benchmark, and it does not support a claim that Ruseact is
faster than React, Solid, Leptos, or another framework.

## Reproduction

From the repository root, run:

```bash
cargo bench -p ruseact-core --bench core_baseline --locked -- --nocapture
```

The custom Cargo bench uses no external benchmarking dependency. It performs
two warmup runs and five measured trials for each case at 16, 64, and 256
signals. The reported median and p95 values are total elapsed nanoseconds for
the timed operation set; `median_ns_per_operation` and
`median_operations_per_second` normalize the median. Fixture construction is
outside timed sections where the operation can be prepared independently.

## Environment and provenance

- Repository: `MaduroLabs/ruseact`
- Benchmark source SHA: `9ec31031a38c84de25b356b0a29eb1af8e1e44cd`
- Host: Linux x86_64, Linux `6.18.60-instabox`, 4 logical CPUs, AMD EPYC
- Rust: `1.99.0` (`x86_64-unknown-linux-gnu`, LLVM `23.1.1`)
- Cargo profile: optimized `bench`
- Workload sizes: 16, 64, and 256 signals; four dependencies per computation
- Trials: 5 measured, 2 warmups
- Date: 2026-11-18 UTC

The benchmark is intentionally deterministic in graph construction and input
values. Wall-clock measurements are host-dependent; reruns should compare the
same operation, workload size, toolchain, and environment rather than treating
the values as universal thresholds.

## Findings

Verified by tests and measurements:

- The 35 core tests pass, including the 1,500-operation deterministic
  reference-model stress test and 256 lifecycle churn cycles.
- Signal reads and equality-aware writes remain independent of graph size in
  this fixture because they address one typed slot; graph construction and
  edge registration increase with the number of allocated items.
- Dirty propagation plus draining reports one affected computation in this
  fixture and exercises the queue coalescing boundary on every iteration.
- The benchmark is stable enough to reproduce the operation shape, but the
  small absolute timings are sensitive to host scheduling and should not be
  treated as pass/fail limits.

Theoretical or design-level findings, not optimization claims:

- Changed writes copy the subscriber list and then visit each subscriber, so
  propagation is O(number of subscribers) before queue deduplication.
- Queue draining is O(number of queued computations), with stale IDs checked
  defensively as they are removed.
- Dependency replacement uses `Vec` membership and edge-list cleanup, so its
  worst-case work grows with requested dependencies and existing edges.
- Disposal cleans both directions and removes pending work; cleanup cost grows
  with the affected dependency or subscriber set.
- Type-erased signal values and per-edge `Vec` storage allocate on the Rust
  heap. Allocation profiling and memory measurements are deferred until there
  is a representative host/WASM integration workload.

No correctness defect was found in the established M1.1–M1.4 API contract, so
M1.5 makes no speculative runtime optimization and adds no dependency.
