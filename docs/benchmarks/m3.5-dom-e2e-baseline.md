# M3.5 End-to-End DOM Integration and Benchmark

## Purpose

M3.5 verifies and measures the existing internal Ruseact path from a real
RustReactiveCore signal update to a targeted native Chromium DOM mutation:

```text
signal write → dirty propagation → WASM bridge → TypeScript handle lookup →
explicit binding update → DOM host operation
```

This is a validation milestone. It does not add a public renderer API,
components, JSX, automatic tracking, scheduling, or a new reactive engine.

## Scope and test fixture

The correctness harness uses the actual generated web WASM bindings, a real
`ReactiveCore`, the internal `createRootContext()`, explicit bindings, and
native DOM nodes. Its small imperative counter has count text, increment and
decrement buttons, and a supported reactive property. Native click events
change the real signal; the DOM remains unchanged until the test calls the
explicit root flush.

The suite also covers unchanged writes, repeated-write deduplication, nested
batching, FIFO ordering, deferred writes during a flush, reentrant flush
rejection, stable node identity, unmount cleanup, rollback, detached and
foreign nodes, duplicate containers, runtime-sharing rejection, independent
roots, borrowed-resource survival, and container reuse.

Run the correctness harness in the supported hosted browser environment with:

```bash
corepack pnpm test:browser:e2e
```

The existing M2, M3.2, M3.3, and M3.4 browser harnesses remain separate and
continue to run in the same CI workflow.

## Benchmark workloads and boundaries

The M3.5 benchmark uses binding sizes 1, 10, 100, and 1000. It records each
row's setup, timed operation, validation, and cleanup boundaries, including
the actual calibrated operation count. The Ruseact workload matrix contains:

- initial root mount;
- unchanged signal writes;
- changed signal write plus explicit flush;
- multiple signal writes followed by one flush;
- several bindings sharing one signal;
- independent signal bindings;
- attribute and supported property updates;
- root unmount and cleanup; and
- repeated root lifecycle cycles.

The native reference matrix repeats only comparable DOM host shapes: element
and text construction, text updates, attribute/property mutation, removal,
and lifecycle cycles. It has no reactive graph, WASM crossing, binding lookup,
explicit flush, or root ownership. It is therefore a host-operation reference,
not a framework comparison.

## Methodology and integrity

The browser benchmark uses a real monotonic `performance.now()` clock and a
DevTools Protocol completion signal. It does not use Chromium virtual time or
`--dump-dom` for performance timing. Each workload is warmed up, calibrated
with the established bounded M2.5 procedure, measured over independent trials,
and validated after timing. Samples must be finite and positive; no sample is
filtered, clamped, or replaced. The report records medians, distribution
metadata, timer information, calibration attempts, operation counts, and an
integrity status. A row that cannot be measured reliably remains unresolved
and fails strict validation.

The benchmark currently requires a complete 9-workload Ruseact × 4-size and
5-workload native × 4-size matrix (56 rows). No absolute speed threshold is a
merge gate. Correctness assertions are independent of timing validity.

The reproducible commands are:

```bash
cargo build -p ruseact-wasm --target wasm32-unknown-unknown --release --locked
wasm-bindgen target/wasm32-unknown-unknown/release/ruseact_wasm.wasm \
  --target web --out-dir target/m3.5-browser-bindgen
RUSEACT_BROWSER_BINDGEN_OUT="$PWD/target/m3.5-browser-bindgen" \
  corepack pnpm test:browser:e2e

RUSEACT_BROWSER_BINDGEN_OUT="$PWD/target/m3.5-browser-bindgen" \
RUSEACT_M35_BENCHMARK_OUT="$PWD/target/m3.5-results/dom-results.json" \
RUSEACT_M35_BENCHMARK_SUMMARY_OUT="$PWD/target/m3.5-results/dom-summary.md" \
  corepack pnpm benchmark:browser:dom
corepack pnpm benchmark:dom:validate \
  target/m3.5-results/dom-results.json
```

The hosted workflow uses the repository-pinned Node, pnpm, Rust, TypeScript,
and `wasm-bindgen` versions. Browser version, commit SHA, and timer metadata
are recorded in the JSON artifact. The current InstaBox cannot reliably route
Chromium to its local temporary HTTP server, so local browser execution is not
reported as a pass.

## Results and interpretation

The numeric browser results are intentionally artifact-backed rather than
invented in source control. CI uploads `dom-results.json` and
`dom-summary.md` under the `ruseact-m3.5-dom-benchmark-*` artifact name. The
pull request workflow records the authoritative hosted run URL and artifact
ID after execution. Until that run completes, this document reports harness
scope and integrity rules, not measured numeric performance.

Verified observations are limited to correctness and measurement boundaries:

- **Verified:** the harness uses the real WASM module, internal root/binding
  contexts, native DOM operations, explicit flushes, bounded workloads, and
  strict result validation.
- **Theoretical:** the full signal-to-DOM path includes graph propagation,
  bridge conversion, TypeScript lookup, binding execution, and host mutation;
  each can contribute to end-to-end cost.
- **Hypotheses:** fan-out, repeated root lifecycle work, and string or property
  mutation may become renderer bottlenecks; application-level profiling is
  required before attributing a measured difference to one layer.

No comparison with React, Solid, Vue, or another framework is made. Raw timing
values from different hosts are not directly comparable.

## Limitations and handoff

M3.5 measures the internal imperative prototype only. It does not establish
public root or view contracts, component identity, compiler output, keyed list
behavior, hydration, scheduling, or automatic dependency tracking. Separate
active roots still require dedicated `ReactiveCore` instances because pending
draining is global and destructive. Browser measurements are authoritative
only on the hosted CI runner, and timing remains subject to that runner's
browser and system load.

The next milestone should use these fixtures to profile renderer-level
behavior after the public lifecycle and view/compiler contracts receive human
approval. Candidate follow-ups are binding lookup profiling, DOM mutation
counting, larger but bounded list workloads, and memory-retention checks after
unmount; none are implemented or inferred by this baseline.
