# M4.4.3 Conditional Structural Regions

Status: implementation on `feature/m4.4.3-conditional-regions`; hosted
Chromium verification is required before the feature is considered complete.
This document records the approved conditional subset only. Keyed lists,
general reconciliation, automatic tracking, and scheduling remain deferred.

## Scope

M4.4.3 extends the existing `ruseact.template` protocol with version 3. It
reuses the M4.2 root façade, M4.4.2 component owners, M3.3 `BindingContext`,
and the RustReactiveCore pending queue. It does not add a second renderer,
reactive graph, binding context, scheduler, virtual DOM, or WASM ABI.

Version compatibility is explicit:

- Version 1: static nodes, scalar bindings, and native listeners.
- Version 2: version-1 capabilities plus static function component placement.
- Version 3: versions 1 and 2 plus approved conditional regions.

Older plans do not accept conditional instructions, and version 3 does not
accept keyed-list instructions.

## Conditional plan

The public renderer exposes the narrow plan shape needed by version 3:

```ts
interface ConditionalRegionPlan {
  readonly kind: "conditional";
  readonly id: string;
  readonly parentId?: string;
  readonly order: number;
  readonly dependencies: readonly SignalHandle<SupportedScalar>[];
  readonly evaluate: (context: BindingEvaluationContext) => RendererResult<boolean>;
  readonly whenTrue: ConditionalBranchFactory;
  readonly whenFalse: ConditionalBranchFactory;
}

interface ViewInstancePlanV3 extends ViewInstancePlanV2 {
  readonly conditions: readonly ConditionalRegionPlan[];
}
```

The renderer validates exactly one explicit signal dependency, a callable
evaluator, and two lazy branch factories. The evaluator must return a
structured boolean result. It does not coerce numbers, strings, or other
values to booleans. The inactive factory is never called. The plan is an
immutable mount description, not an updateable UI tree.

The compiler has a provisional, compiler-only marker:

```tsx
ruseact.conditional(
  [enabled],
  ({ runtime }) => runtime.get(enabled),
  () => <p>enabled</p>,
  () => <p>disabled</p>,
)
```

This marker is deliberately narrower than a general JSX ternary and does not
make arbitrary identifiers reactive. A future public authoring contract would
require separate approval.

## Private anchors and range safety

Each region creates two renderer-managed `Comment` nodes in the owner
document. They are inserted in order and remain stable across branch changes.
Branch roots are inserted strictly before the end anchor. The host accepts
comment nodes only through its private `createAnchor()` capability; comments
cannot be scalar text-binding targets or adopted across roots/documents.

Before changing a live region, the renderer verifies:

- the owner, anchors, and expected parent are live;
- both anchors belong to the host document and host context;
- the start anchor precedes the end anchor;
- active branch roots remain direct children of the expected parent;
- renderer ownership is valid for every node in the active range; and
- no foreign or detached node is silently adopted or removed.

Unexpected external DOM interference is a structured failure. The renderer
does not promise recovery from arbitrary application DOM mutation.

## Branch lifetime and cleanup

The initial selector evaluation creates exactly one branch activation. A
changed selector follows this sequence:

1. Validate the region and range.
2. Dispose the active branch and descendants child-first.
3. Dispose its bindings, subscriptions, listeners, and owned DOM resources.
4. Create a provisional owner for a fresh activation.
5. Execute only the selected factory.
6. Validate and mount its static/component plan before the end anchor.
7. Run initial scalar bindings and publish the new owner.

`false -> true -> false` therefore creates three activation lifetimes. An
inactive branch is not cached and its listeners/computations are not retained.
An unchanged selector does not dispose or recreate anything, and the parent
component never reruns.

If selector evaluation fails before mutation, the active branch is preserved.
If old cleanup succeeds but new branch initialization fails, renderer-managed
new resources are rolled back, the anchors remain, and the region is safely
empty. The old branch is not reconstructed and the renderer does not retry
automatically. If cleanup cannot establish safe ownership, the region/root
enters a fail-closed cleanup state and retains the relevant records. These
guarantees do not reverse arbitrary JavaScript side effects.

## Shared flush semantics

Structural records are ordinary Rust-backed computations registered in the
root's existing `BindingContext`. Scalar and structural records share:

- computation creation and explicit dependency replacement;
- the Rust dirty queue and first-dirty FIFO ordering;
- one destructive pending snapshot per `root.flush()`;
- queue deduplication;
- reentrant flush rejection; and
- deferred work generated during a flush.

The complete snapshot is validated before execution. During dispatch, a
structural update may successfully dispose a later exact record from that
snapshot. Only that exact renderer-owned computation can be skipped. The
record must have belonged to this context, appeared in the validated snapshot,
been disposed by renderer-managed cleanup during the current flush, and
completed disposal successfully. Such a record increments
`FlushReport.skippedCount`; `drainedCount` still includes it and unrelated
live records continue.

Unknown, foreign, malformed, unexpectedly missing, or unsuccessfully disposed
records fail closed. A reused computation slot cannot make an old snapshot
record equal to a newly created record because identity includes the opaque
computation generation. Newly generated pending work is not recursively
drained.

## Ownership

The ownership hierarchy is:

```text
RendererRoot
└── component owner / static scope
    └── conditional region owner
        ├── start and end anchors
        ├── structural selector computation
        └── active branch owner
            ├── component owners
            ├── scalar bindings
            ├── listeners
            └── DOM nodes
```

There is one authoritative cleanup path. Child owners are disposed before
parent resources, and resources inside an owner are released in reverse
registration order. Completed branch owners are released from their parent
registry after successful disposal, preventing unbounded completed-record
growth during repeated switching. Borrowed runtimes, application signals, and
containers are never disposed by a region.

## Compiler and tests

`packages/ruseact-compiler` emits version 3 only when the conditional marker
is present. It preserves lexical closures, lazy factory references, explicit
dependencies, deterministic region IDs, and source diagnostics. Existing
version-1 and version-2 output is unchanged.

Compiler tests cover deterministic IDs, explicit dependency validation, lazy
factories, empty/multi-node branches, lexical closure behavior, and rejection
of implicit or unsupported structural syntax.

The authoritative browser harness is:

```bash
RUSEACT_BROWSER_BINDGEN_OUT=target/m4.4.3-browser-bindgen \
  corepack pnpm test:browser:conditional
```

It uses real Rust/WASM and Chromium and covers initial true/false selection,
stable anchors, unchanged selectors, empty and multi-node branches, nested
components, input/focus preservation outside the region, same-snapshot skip
counts, generated-work deferral, failed replacement, cleanup failure,
detached anchors, DocumentFragment roots, and repeated switching. Existing
M3/M4 browser suites remain separate regression gates.

## Limitations and M4.4.4 handoff

The implementation does not provide keyed lists, duplicate-key policy,
SameValueZero key equality, retained item updates, native range reordering,
unkeyed reconciliation, automatic scheduling, automatic dependency tracking,
recursive flushing, keep-alive branches, retries, focus restoration, error
boundaries, hydration, SSR, portals, async branches, or public comment APIs.

M4.4.4 must define key equality and duplicate-key behavior before implementing
retained item ownership or DOM movement. It must preserve version 1, version 2,
and version 3 validation, the shared pending queue, child-first cleanup, and
the fail-closed ownership rules established here.
