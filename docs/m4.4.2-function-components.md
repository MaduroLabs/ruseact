# M4.4.2 Function Components and Nested Ownership

Status: implementation on `feature/m4.4.2-function-components`; the public
contract remains subject to review in the feature pull request. This milestone
implements only the six decisions approved for M4.4.2. Conditional regions,
keyed lists, component rerendering, hooks, and scheduling remain deferred.

## Scope and verified baseline

M4.2 provides `createRoot(container, runtime)`, one-shot static mount plans,
scalar binding slots, native listeners, structured `RendererResult` values,
and deterministic manual flush. M4.3 emits version-1 plans from a narrow TSX
subset using the TypeScript Compiler API and explicit dependency markers.

M4.4.2 extends that same renderer pipeline with statically placed component
instances. It does not create a second renderer, binding context, reactive
graph, DOM ownership registry, scheduler, or WASM operation.

## Public component contract

The public `ruseact-dom` entry point now exposes the narrow component types and
the `defineComponent(typeId, setup)` helper:

```ts
const Heading = defineComponent("Heading", (props, environment) => {
  const label = typeof props.label === "string" ? props.label : "";
  return {
    ok: true,
    value: {
      protocol: "ruseact.template",
      version: 1,
      templateId: "heading",
      instantiate: () => ({
        nodes: [
          { id: "heading", kind: "element", name: "h1" },
          { id: "text", kind: "text", parentId: "heading", text: label },
        ],
        bindings: [],
        listeners: [],
      }),
    },
  };
});
```

`ComponentDefinition` contains a stable `typeId` and a setup function. Setup
receives an immutable, shallow props snapshot and a narrow environment with the
borrowed runtime and deterministic instance identity. It returns a structured
`RendererResult<ComponentView>`. It is called once for each successfully
initialized instance; a signal update never calls it again.

Props may contain booleans, numbers, strings, `undefined`, or existing typed
`SignalHandle` references. The renderer copies and freezes the props record,
but does not recursively freeze application objects because arbitrary object
signals are outside the scalar contract. Signal-handle props are read by a
binding evaluator through the existing runtime, so they do not become stale
captured values.

## Version 2 mount plans

Version 1 is unchanged and remains the output for intrinsic-only M4.3 views.
Version 2 uses the same protocol string and adds only static component
placements:

```ts
interface ViewInstancePlanV2 extends ViewInstancePlan {
  readonly components: readonly ComponentPlacementPlan[];
}

interface ComponentPlacementPlan {
  readonly kind: "component";
  readonly id: string;        // deterministic local instance slot
  readonly parentId?: string; // static element in this plan, or root
  readonly order: number;
  readonly component: ComponentDefinition;
  readonly props?: ComponentProps;
}
```

Static nodes in a version-2 plan may carry a local sibling `order`. The
executor merges static nodes and component placements by `(parentId, order,
plan order)`, which makes mixed static/component ordering deterministic without
maintaining a mutable virtual tree. Child plans are lowered into the same
executor; nested components do not call `createRoot`.

Version 2 deliberately contains no conditional-region, list, anchor, update,
or reconciliation instruction. A component's returned version-1 description
or instance plan is materialized once during setup. A returned version-2 plan
may contain statically nested component placements.

## Identity

The implementation creates an owner identity from the parent owner path, the
static local placement slot, and the component type ID. The component identity
is independent of `SignalHandle`, `ComputationHandle`, DOM position, and
process-global allocation order. Duplicate placement IDs are rejected during
plan validation; identical local slots beneath different parent owners are
isolated by their parent paths. A component owner is never used as a reactive
computation identity.

Identity is created before setup, remains stable for the mounted lifetime, and
is invalidated by disposal. M4.4.2 has no retained keyed items, so identity is
not matched across updates and there is no key-equality policy yet.

## Setup and ownership sequence

For each placement the renderer:

1. Validates the component definition, slot, parent, and scalar props.
2. Creates a provisional child owner beneath the parent owner.
3. Snapshots props without mutating the caller's object.
4. Invokes setup exactly once with the borrowed runtime and owner identity.
5. Materializes and validates the returned version-1 or version-2 plan.
6. Creates DOM nodes through the existing `RootMountScope`.
7. Registers binding computations in the root's existing `BindingContext`.
8. Initializes nested component owners.
9. Publishes the owner only after managed initialization succeeds.

Every successfully registered binding is tracked by its component owner and is
disposed through the existing binding context. Native listeners and created
DOM nodes remain in the root host's single authoritative registry; this avoids
two independent registries trying to remove the same listener or node. The
root cleanup callback disposes the owner hierarchy before the binding context
and host context perform their final cleanup.

## Child-first cleanup and rollback

Owner disposal is child-first and reverse-registration ordered:

```text
descendant owners (reverse order)
  -> owner bindings/resources (reverse order)
  -> parent owner
  -> root binding context and host context
```

This ensures a child binding cannot execute against a parent subtree that has
already been removed. Disposal is idempotent after success and does not
double-dispose a binding. A cleanup failure leaves the owner in
`cleanup_failed`; the root preserves its fail-closed cleanup state and reports
the original cause and cleanup diagnostics where available.

If setup, plan validation, node creation, binding registration, listener
registration, nested setup, or host mutation fails, the provisional owner is
disposed and its managed resources are released. The existing root rollback
then cleans the remaining root resources. Arbitrary application side effects
performed inside a component function are not claimed to be transactional.

Application signals, the supplied `ReactiveCore`, and the container are
borrowed. Component cleanup never disposes them. A root continues to require a
dedicated runtime while mounted because pending computation draining is still
runtime-global and destructive.

## Compiler support

The M4.3 compiler now accepts statically named uppercase JSX references such
as:

```tsx
<section>
  <Heading label="Title" />
  <Counter count={countSignal} />
</section>
```

It emits version 2 when a component placement is present, with deterministic
`c0`, `c1`, ... slots, explicit props expressions, stable order metadata, and
component slot source metadata. The component reference is an ordinary
lexical JavaScript value; the compiler does not invoke it, serialize it, or
construct a handle. The application must provide a `ComponentDefinition`,
normally through `defineComponent`.

Supported component props are scalar literals/expressions and explicit signal
handle references. Spread props, component children, dynamic component tag
expressions, fragments, conditional structure, lists, hooks, and implicit
dependency inference are rejected with source-located diagnostics. Intrinsic-
only JSX keeps version-1 output and existing generated modules remain valid.

## Reactive semantics

Bindings remain ordinary root-owned Rust-backed computations:

```text
signal write
  -> RustReactiveCore invalidation
  -> WASM pending identity transfer
  -> TypeScript binding lookup
  -> JavaScript evaluator
  -> native DOM mutation
```

Component identity is not placed in that queue. `root.flush()` remains one
destructive pending snapshot, FIFO and deduplicated, with reentrant flush
rejection and deferred work. A signal update can update several explicitly
subscribed component bindings, but cannot rerun a component setup function or
reconstruct unrelated DOM.

## Browser verification

The hosted Chromium compiler harness executes the actual generated WASM
runtime, public renderer, and compiler output. Its M4.4.2 fixture covers:

- a compiled parent with a nested `Panel` and `Heading` component;
- two independent `Counter` instances with distinct signal-handle props;
- instance-specific native event closures;
- explicit flush and no-update-before-flush behavior;
- stable text and element identities;
- setup-once behavior after multiple signal updates;
- child unmount listener cleanup, root disposal, and borrowed runtime safety.

The local InstaBox loopback server is not authoritative when its sandbox
prevents `127.0.0.1` binding; hosted Chromium remains the required browser
environment. Compiler unit tests cover deterministic version-2 output,
component slots, props, and unsupported dynamic tags.

## Deferred capabilities and M4.4.3 handoff

M4.4.2 does not implement conditional regions, comment anchors, structural
computations, keyed lists, key equality, retained-item updates, component
rerendering, automatic tracking, automatic scheduling, hooks, context,
hydration, SSR, portals, async components, or shared-runtime scheduling.

M4.4.3 requires a separate approved contract for anchor nodes, conditional
branch ownership, selector dependencies, one-pass structural updates, and
partial mutation recovery. It must start from a fresh branch and preserve the
version-1/version-2 component contracts established here.
