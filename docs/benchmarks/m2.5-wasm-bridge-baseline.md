# M2.5 WASM bridge performance baseline

## Purpose

M2.5 establishes a reproducible baseline for the existing Ruseact
Rust/WASM/TypeScript runtime. It measures bridge, wrapper, graph metadata,
dirty-work transfer, batching, initialization, and lifecycle costs. It is a
measurement milestone, not an optimization milestone.

The benchmark does not render DOM, execute computation callbacks, schedule
work, compile JSX, or compare Ruseact with React, SolidJS, Vue, or another
framework.

## Measurement scope

The suite keeps four conceptual layers separate:

1. Rust-native behavior remains represented by the unchanged M1.5 Cargo
   benchmark and its existing report.
2. Direct WASM calls use generated `wasm-bindgen` Node or web bindings with
   minimal JavaScript orchestration.
3. TypeScript runtime calls use the public `packages/ruseact` APIs, including
   `CoreResult` handling, instance-owned registries, and pending-handle
   resolution.
4. Browser results use the same TypeScript/WASM runtime inside real Chromium.

Direct WASM and TypeScript rows are comparable only where the workload is the
same. A TypeScript row may additionally include wrapper validation, result
normalization, registry lookup, and public-handle lifecycle work. Those costs
are reported as combined wrapper overhead; the suite does not infer an
isolated crossing cost from non-equivalent rows.

## Workloads and fixture accounting

Every JSON row records graph size, computation count, dependency edges,
subscriber fan-out, affected computations, pending pairs, setup operations,
timed operations, cleanup behavior, raw samples, and summary statistics.

| Fixture | Configuration |
| --- | --- |
| Small | 16 signals |
| Medium | 64 signals |
| Large | 256 signals |
| Default computation graph | `max(1, floor(signals / 4))` computations; degree-4 edges |
| Replacement graph | One computation and 8 dependency edges |
| Fan-out graphs | 1, `max(1, floor(signals / 4))`, and `signals` subscribers |
| Shared-update graphs | Up to 8 signals subscribed to the same computations |
| Repeated operations | 1,024 iterations; signal reads repeat each graph 128 times; short lifecycle and transfer cases start at 64 fixtures and use bounded adaptive calibration |

The timed sections exclude fixture construction whenever the operation can be
measured on an initialized graph. Cleanup is explicit and outside the timed
section except where graph disposal or resource disposal is itself the tested
operation. No computation callback is executed and no scheduler is added.

## Tested operations

- Signal creation, read, changed write, unchanged write, disposal, and
  boolean/number/string scalar conversion.
- Repeated stale-handle validation on the direct bridge and public wrapper.
- Computation creation, direct identity lookup, subscription, duplicate
  subscription, unsubscription, dependency replacement, computation disposal,
  and reverse dependency cleanup.
- Dirty propagation with one, multiple, and size-scaled subscriber fan-out;
  shared-computation updates; queue draining; FIFO/deduplication; and
  re-enqueue after drain.
- Unbatched updates, one explicit batch, nested batches, batch-boundary-only
  work, shared dependent computations, and pending transfer after a batch.
- Cold WASM/runtime initialization, warm instance creation, explicit graph
  disposal, and repeated signal lifecycle operations.
- Direct pending `Uint32Array` transfer and public TypeScript
  `ComputationHandle` resolution.

The public TypeScript API does not expose `computation_identity()` directly.
The direct identity row therefore measures the bridge accessor itself, while
the public pending-transfer rows measure the public registry resolution path.

## Methodology

Each workload runs two warmups and ten measured trials. The harness uses fixed
inputs, a monotonic timer, raw elapsed samples, median, nearest-rank sample
p95, median time per timed operation, and throughput where meaningful.
Correctness checks run outside the timed section and verify scalar values,
changed/unchanged behavior, pending FIFO order, deduplication, pair counts,
generation values, disposal, and re-enqueue behavior. Short operations use
fixed repetition counts recorded in `configuration`; pending transfer uses a
repeated transfer/re-enqueue cycle so a one-subscriber queue is observable
without changing the underlying graph algorithm.

The browser harness records `performance.now()` converted to nanoseconds and
records the smallest observed positive timer increment as
`metadata.timer_resolution_ns`. Before official trials, each workload is
measured from its existing repetition count. Prepared independent states are
then batched outside the timed section until elapsed work reaches at least
`max(2,000,000 ns, 16 * timer_resolution_ns)`, bounded by 64 prepared states
and a 50 ms calibration sample. The 2 ms floor provides a materially larger
margin than the approximately 100 microsecond timer increments observed in
the failing hosted run. The selected batch count, calibration samples, target,
and final timed operation count are recorded in every non-cold row.

Each official measurement attempt includes fresh warmups and measured trials.
If any official sample is zero or non-finite, that complete attempt is
discarded and recalibrated with at least twice the previous batch size. There
are at most three attempts per workload. Previous attempts, their raw samples,
and their operation counts remain in `measurement_attempts`; only the final
attempt supplies the published summary. If the bound is exhausted, the final
row remains unresolved and the strict validator fails. Values are never
clamped, filtered, or replaced. Browser completion is obtained through a
Chromium DevTools Protocol `Runtime.evaluate` poll, with a monotonic Node
timeout; it does not use virtual time or `--dump-dom`.

## Toolchain and reproduction

The repository pins Rust `1.99.0`, Node `24.22.3`, pnpm `12.16.1`,
`wasm-bindgen` `0.2.130`, and the `wasm32-unknown-unknown` target. The
authoritative benchmark workflow is manually dispatched on `ubuntu-latest`;
it does not create a merge gate or a performance threshold.

Build and generate both binding targets:

```bash
cargo build -p ruseact-wasm --target wasm32-unknown-unknown --release --locked
mkdir -p target/m2.5-node-bindgen target/m2.5-browser-bindgen
wasm-bindgen target/wasm32-unknown-unknown/release/ruseact_wasm.wasm \
  --target nodejs --out-dir target/m2.5-node-bindgen
wasm-bindgen target/wasm32-unknown-unknown/release/ruseact_wasm.wasm \
  --target web --out-dir target/m2.5-browser-bindgen
```

Run the Node benchmark and validate its machine-readable output:

```bash
RUSEACT_WASM_BINDGEN_OUT="$PWD/target/m2.5-node-bindgen" \
RUSEACT_BENCHMARK_SOURCE_SHA="$(git rev-parse HEAD)" \
RUSEACT_BENCHMARK_OUT="$PWD/target/m2.5-results/node-results.json" \
RUSEACT_BENCHMARK_SUMMARY_OUT="$PWD/target/m2.5-results/node-summary.md" \
corepack pnpm benchmark:node
corepack pnpm benchmark:validate -- target/m2.5-results/node-results.json
```

Run the real browser benchmark from a supported Chromium environment:

```bash
RUSEACT_BROWSER_BINDGEN_OUT="$PWD/target/m2.5-browser-bindgen" \
RUSEACT_BENCHMARK_SOURCE_SHA="$(git rev-parse HEAD)" \
RUSEACT_BENCHMARK_OUT="$PWD/target/m2.5-results/browser-results.json" \
RUSEACT_BENCHMARK_SUMMARY_OUT="$PWD/target/m2.5-results/browser-summary.md" \
corepack pnpm benchmark:browser
corepack pnpm benchmark:validate -- \
  target/m2.5-results/node-results.json \
  target/m2.5-results/browser-results.json
```

The manual workflow is `.github/workflows/m2.5-benchmark.yml`. It uploads the
JSON and Markdown outputs as the `ruseact-m2.5-benchmark-<sha>` artifact even
when the integrity validator fails, so unresolved measurements remain
inspectable without making the workflow successful.
Generated bindings, `target`, `node_modules`, and machine-local result files
are not committed.

## Timing reliability investigation

Run `44456788741` is the last directly inspected diagnostic evidence before
adaptive calibration: Node reported 263/263 valid workloads, while Chromium
reported 256/263 valid workloads and seven zero-median workloads; all reported
durations were finite. Additional rows had individual zero samples despite a
positive median. The old runner combined `--virtual-time-budget` with
`--dump-dom`, so virtual-time quantization was a credible contributor, but the
artifact does not isolate it as the sole cause.

The corrected runner removes both flags and obtains completion through CDP.
Adaptive calibration now measures each operation first and batches independent
prepared states only when the elapsed work is below the timer-resolution target.
The calibration is bounded and recorded; it cannot convert an unresolved zero
into a positive duration. Hosted Chromium correctness passing confirms real
page execution, but it is not a substitute for a passing benchmark integrity
report.

The corrected adaptive run `44460980319` passed the benchmark integrity gate
for both layers: 263/263 Node rows and 263/263 Chromium rows were valid, with
no unresolved or zero-sample rows. Numeric medians and throughput remain in
artifact `14499858517`; they are not reproduced here because the artifact ZIP
was unavailable to this session.

The later hosted run `44498872905` reproduced the remaining intermittent case:
Node had 263/263 valid rows, while Chromium had 262/263. The failing row was
`direct-wasm/signal_write_changed/16` and contained one zero sample alongside
positive samples and a positive median. This evidence does not demonstrate a
RustReactiveCore defect. It demonstrates that the prior 100 microsecond floor
and single calibration decision could still accept a batch whose official
sample was vulnerable to timer quantization or browser scheduling. The
maintenance calibration now uses the 2 ms floor and bounded whole-attempt
recalibration described above. Calibration regression tests simulate quantized
and intermittent clocks without weakening the production validator.

## Analysis categories

### Verified

Only measurements from the completed JSON artifacts belong in this section.
They should identify observed high-cost operations, graph-size trends,
pending transfer behavior, and direct-versus-public-runtime differences for
the same fixture and operation.

### Theoretical

The existing implementation copies subscriber lists during changed writes,
uses FIFO dirty-queue deduplication, and performs `Vec`-backed dependency
membership and cleanup. These structures imply growth with subscriber count,
pending queue length, and dependency/edge cleanup work. This is complexity
analysis, not a claim about a measured constant or universal runtime speed.

### Hypothesis

Future DOM work may make pending-work transfer, public handle resolution,
string conversion, dependency replacement, and repeated per-binding calls
important bottlenecks. These hypotheses require application-level renderer
benchmarks after a DOM renderer and compiler exist.

## Limitations

- Raw times are host- and runner-dependent and must not be compared across
  machines as absolute performance rankings.
- Node diagnostics on this InstaBox use Node 22 when the pinned Node 24 binary
  is unavailable; hosted Node artifacts are authoritative for pinned results.
- Browser timer resolution and browser scheduling constrain small timings.
- Cold initialization includes module import/instantiation under the harness
  boundary; it is not a process-startup measurement.
- Public TypeScript rows include wrapper and registry work that direct rows do
  not. They are not a proof of an isolated JS-to-WASM crossing cost.
- Error-normalization cost is not isolated: the public runtime rejects a stale
  wrapper before calling the bridge, and forging a raw `WasmHandle` would
  violate the established identity contract. Stale validation is measured;
  bridge error normalization remains a combined, non-isolated behavior.
- Pending drain follows the existing destructive-drain contract. No
  acknowledgement, rollback, scheduler, or bulk `setMany()` protocol was
  introduced.
- No memory-leak or memory-freedom claim is made. This benchmark records time,
  not JS heap or WASM linear-memory usage.

## M3 DOM renderer handoff

M3 should use these rows as a bridge baseline when adding a renderer. It should
add separate measurements for component execution, DOM commit, event wiring,
and any compiler-generated batching or bulk transfer. It must preserve the
distinction between fewer public calls and cheaper individual calls, and it
must not treat this milestone as evidence of framework-wide performance.
