# M4.4.5 Owner-Scoped Structural Identity Hardening

## Status and scope

M4.4.5 fixes the structural registration identity collision discovered by the
independent consumer Conditional Playground. It is an internal
`ruseact-dom` correction; it does not add a renderer protocol, public API,
scheduler, reactive engine, or Rust/WASM ABI change.

The existing compiler is allowed to reuse template-local region IDs such as
`r0` in independent component and branch plans. Those IDs remain unchanged in
compiler output and public version-3/version-4 plan metadata.

## Defect and root cause

Before M4.4.5, conditional registration used the raw local ID:

```ts
scope.registerStructural({
  dependencies: condition.dependencies,
  key: condition.id,
  update,
});
```

`BindingContext` kept one `Set<string>` for structural keys. An outer
conditional and a conditional in a component mounted by that branch could
therefore both register `r0` in the same root binding context and the nested
mount failed with a wrapped `child_mount_failed` diagnostic.

Keyed lists used a different string encoding based on the diagnostic owner ID.
That made the two structural kinds inconsistent and made concatenated owner
IDs appear to be an authoritative identity model even though they are only
diagnostic strings.

## Internal identity model

The binding context now keeps structural registrations in a private weakly
scoped registry:

```text
WeakMap<owner object,
  Map<local region ID, structural record>>
```

The renderer supplies the exact private `ComponentOwner` object as the scope
and records the structural kind as `conditional` or `keyed`. Equal local IDs
in different owner instances do not collide. A duplicate local ID in one owner
remains rejected across structural kinds. Conditional and keyed registration
use the same scoped identity mechanism; keyed registration no longer embeds
`owner.id` into a string key.

The scope object is internal and is not exported through the public package
entry point. Computation handles remain the authoritative pending-dispatch
identity; owner scope is only the structural registration namespace.

## Registration and cleanup

The scoped identity is reserved before the registration's initial structural
evaluation. This prevents nested registration during initial evaluation from
overwriting or bypassing duplicate detection.

Successful cleanup releases the exact structural record and its scoped local
identity. If dependency unsubscription or computation disposal fails, the
record and scoped identity remain retained, the context remains reserved for
the runtime, and subsequent work fails closed. A failed record is never
treated as a successfully disposed same-snapshot record.

Successful disposal still releases completed records, so repeated activation
does not accumulate structural identities. Root cleanup continues to dispose
the shared binding context and host through the existing child-first path.

## Pending queue compatibility

M4.4.5 does not change Rust dirty propagation, pending-drain ABI, FIFO
snapshot ordering, reentrant-flush rejection, exact computation identity
matching, deferred generated work, or the verified same-snapshot skip rule.
Scoped local-ID equality never authorizes a skip; only the exact successfully
disposed computation record can be skipped and counted in
`FlushReport.skippedCount`.

## Verification

The real Rust/WASM Chromium conditional harness covers 217 checks, including:

- nested outer and inner `r0` conditionals;
- repeated component instances with independent `r0` regions;
- fresh branch activation and descendant cleanup;
- conditionals inside keyed items and keyed lists inside conditional branches;
- retained keyed range movement;
- same-snapshot disposal of an exact nested computation while an unrelated
  same-ID region remains live; and
- duplicate local IDs in one plan remaining rejected.

Existing compiler and keyed-list browser suites remain separate regression
gates. Protocol versions 1–4 remain unchanged.

## Consumer handoff

The previously vendored `0.1.0-alpha.0` artifacts intentionally remain
unchanged in the consumer repository. After this fix is merged and promoted,
the distribution pipeline must produce a new matching experimental artifact
set, preferably `0.1.0-alpha.1`, with new checksums and provenance. The
consumer must update all three tarballs as one reviewed set before resuming
the Conditional Playground.
